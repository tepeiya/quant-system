📦 每个模块内部结构

📡 数据模块 (data_service)
职责：只管"把行情变成指标"
输入：定时器 tick / 手动触发
输出：写入 data_cache/
不关心：策略怎么用这些数据、有没有交易信号
挂了→：其他模块读缓存，等它恢复
🧮 策略模块 (strategy_*)
职责：只管"算信号"，不交易
输入：从 data_cache 读价格/指标
输出：写入 signal_queue (消息总线)
不关心：Alpaca是什么、钱够不够
策略间：彼此无依赖，独立计算
🛡️ 风控模块 (risk_service)
职责：从总线读"准备下单"的消息→检查→通过/拦截
输入：持仓数据 + 市场数据 + 订单意图
输出：允许/拒绝 + 风控日志
边界：只判断"能不能做"，不做"做什么"
💹 执行模块 (executor)
职责：从总线读信号→问风控→下单→写成交回报
输入：信号消息 + 风控审批
输出：成交记录 + 订单状态更新
抽象：不关心信号来源，不关心是哪个策略

🔗 消息总线：模块之间的"那条线"

什么是消息总线？ 每个模块不直接调另一个模块的函数，而是往总线上"发消息"，其他模块从总线上订阅自己感兴趣的消息。模块之间完全解耦。
🗄️ 选项A: SQLite + 状态表 (轻量，推荐先做)
signal_queue 表：策略写入信号，执行器扫描处理
order_queue 表：执行器写入订单状态
risk_events 表：风控事件日志
优点：不需要额外服务，现有代码改动最小
缺点：多个进程需要轮询，不是实时推送
📨 选项B: ZeroMQ (专业，后续升级)
PUB-SUB 模式：数据模块发布行情→策略订阅→发布信号→执行器订阅
优点：实时推送、多语言支持、高可靠
缺点：多一个服务要管理，部署复杂一点
📡 选项C: Redis Streams (最推荐终版)
Stream：类似 Kafka 但轻量，每个消费组独立 offset
优点：实时推送、消息持久化、消费者挂了恢复后不漏消息
缺点：要跑 Redis，多一个依赖

⚡ 分步实施方案（不改停现有系统）

阶段一：统一信号格式 + 订单总线（SQLite）

1-2天，不动交易逻辑
创建一个 signal_bus.py，定义统一的消息格式。三个策略各自改成"计算结果→写入 signal_queue 表"而不是直接调 Alpaca。执行器改成"从 signal_queue 读→下单"。现有代码不动，只加新模块。

阶段二：风控管道化

0.5天
在 executor 调 Alpaca 之前统一过 risk_manager.check()，不再依赖每个交易器自己记得加风控。

阶段三：数据模块独立

1天
把 data_prod / data_global / cache_manager 抽成 data_service 独立进程。其他模块通过 cache 文件或 Redis 读数据。

阶段四：策略热插拔

按需
每个策略变成 plugins/ 下的独立目录（strategy_vector / strategy_momentum / intraday / futures_pairs / wheel），系统启动时自动扫描加载。停用一个策略=从 plugins 目录移走，不会影响其他策略。
